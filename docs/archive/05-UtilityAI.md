# 05 — Utility AI

本文件规定个体"怎么决定下一步做什么"。这是整个项目里**最需要可解释性**的部分：
玩家看到一个人不动了，必须能查清他为什么不动，而不是猜。

---

## 1. 为什么用 Utility AI 而不是行为树 / 状态机

| 方案 | 问题 |
|---|---|
| **行为树** | 需要预先编排结构。"优先级 + 条件"实际上是设计师替个体做了决定，很难产生"因人而异"的行为 |
| **有限状态机** | 状态之间的迁移是硬编码的。加一个需求就要加一圈迁移，状态数爆炸 |
| **Utility AI** | 每个动作独立打分，取最高分。加一个动作只需要加一条定义；参数可调；**打分过程本身就是解释** |

关键区别：行为树回答"接下来该走哪条分支"，Utility AI 回答"此刻哪件事最值得做"。
后者天然适合"需求驱动的日常生活"，而且**不需要预言全世界的可能状态** ——
这对一个涌现型沙盒至关重要（设计师不可能预见到所有局面）。

---

## 2. 四层结构

```text
Consideration（考虑项）
  把某个输入映射成 [0,1] 的分数
        ↓
ActionScore（动作得分）
  若干 Consideration 组合成该动作的效用 + 保留全部分解
        ↓
UtilityBreakdown（决策结果）
  所有候选动作的分数排序 + 最终选择（存在个体身上，供检查器显示）
        ↓
ActionSystem（执行）
  移动 → 执行 → 结算 / 失败（与决策完全解耦）
```

对应源码：`Ai/UtilityBreakdown.cs`、`Systems/ScoreBuilder.cs`、`Systems/AiSystem.cs`、
`Systems/ActionSystem.cs`、`Systems/Actions/*`。

---

## 3. 考虑项（Consideration）

一条考虑项 = 名字 + 输入 + 曲线 + 权重。

```csharp
b.Consider("饥饿", hunger, UtilityCurve.Survival, w.GatherFoodHungerWeight);
//          ↑名字   ↑输入[0,1]  ↑曲线                  ↑权重（可负 = 惩罚项）
```

- **输入必须归一化到 [0,1]**（第 16 条）。这样不同系统的数值尺度不会互相污染。
- **曲线决定"紧迫感从哪里开始"**（第 17 条）。
- **权重决定"这件事相对于其他因素有多重要"**。负权重表示惩罚（例如"背包里已有食物"会降低采集欲望）。

### 3.1 可用曲线

| 曲线 | 公式 | 语义 | 典型用途 |
|---|---|---|---|
| `Linear` | `x` | 中性 | 一般权重项 |
| `Quadratic` | `x²` | 低需求时几乎不想做 | 非生存类动作的"抑制项" |
| `Sqrt` | `√x` | 稍有需求就有明显倾向 | 温和型行为 |
| `Survival` | `1−(1−x)²` | **低需求区就快速抬升** | 生存类动作（吃/喝/睡/采食） |
| `Logistic` | 归一化 logistic | 阈值型：不到阈值几乎不做 | "够了就停"类条件 |
| `InverseLogistic` | `1−L(1−x)`，单调递增 | 条件越好越想抓 | 机会型行为 |
| `Step` | `x≥t ? 1 : 0` | 硬门 | 前置条件（手上有食物 / 附近有水） |
| `SmoothStep` | S 曲线 | 平滑过渡 | 距离/强度衰减 |
| `Constant` | 常数 | 纯权重项 | "基础倾向" |

### 3.2 `Survival` 曲线为什么必须存在（一次真实的踩坑）

效用合成器里带了**补偿因子**（见 §4），这带来一个副作用：

> 任何一个"被门挡住"的动作，其效用会停在一个**下界**上，而不是 0。

实测后果：如果食物采集在"有点饿"时打分低于"顺手砍柴"，
个体就会一直砍柴直到饿死 —— 真的发生过：**40 人全饿死，采集统计里食物量为 0**。

`Survival` 曲线 `1−(1−x)²` 在低输入区就快速抬升（`x=0.3 ⇒ 0.51`），
于是"刚开始饿"就能压过非生存行为。它仍然单调递增且有界，符合效用系统的硬性要求。

这条经验的通用形式：**当合成器带补偿时，"该压过别的动作的动作"必须在低输入区就拿到高分**，
否则补偿项会把它永远按在下面。

## 4. 效用合成（`UtilityCombiner`）

```text
linear = Σ(wᵢ · sᵢ) / Σ|wᵢ|                       加权算术平均
geom   = exp( Σ(wᵢ · ln(sᵢ + ε)) / Σ|wᵢ| )         加权几何均值（ε = 0.02）
U      = √(linear × geom)                           两者折中
```

### 4.1 为什么折中

| 方案 | 问题 |
|---|---|
| 纯算术平均 | 任一条件差都能被其他条件补偿 ⇒ 出现"其实不能做但硬要做"的行为 |
| 纯几何均值 | 任一项为 0 则整体为 0 ⇒ 行为僵硬；权重为负时数学不成立 |
| **折中** | 高权重项接近 0 会把效用压得很低（接近硬门），但不至于锁死 |

### 4.2 负权重（惩罚项）的处理

负权重项按"惩罚"处理：把权重搬到正区间（`w' = -w`），对分数取补（`1 - s`），
于是它在数学上等价于一个正权重项。这样几何均值仍然有定义。

**这是有代价的**：惩罚项永远不会把效用变成 0（因为补偿项仍在）。
因此**惩罚适合表达"倾向"，不适合表达"禁止"**。真正的禁止要用 `Step` 硬门。

### 4.3 "被门挡住"的处理

当某个正权重项的分数 ≤ 0.05 时，标记 `blocked`，最终效用乘以
`AiConfig.BlockedUtilityMultiplier`（默认 0.15）。

**注意不能直接归零**：否则"手上一粒粮食都没有"的人会连"去找吃的"都不做
（那一步的效用本身就是 0）。真正的互斥应该由动作之间的竞争解决。

## 5. 动作定义（M1 实装 8 个）

动作登记在 `Systems/ActionDef.cs` 的 `ActionRegistry` 里，**数据驱动**：
新增动作只需加一条定义（效用函数 + 选靶函数），决策循环、检查器、测试都不用改。

| 动作 | 需要目标 | 效用考虑项 | 说明 |
|---|---|---|---|
| `Eat` | 否 | 饥饿（Survival, 2.0）、手上有食物（Step, 1.2） | 原地进食，每 tick 消耗 0.6 食物 |
| `Drink` | 是（临水格） | 干渴（Survival, 2.2）、附近有水（Linear, 0.8） | 站岸边喝水 |
| `Sleep` | 否 | 疲劳（Survival, 2.0）、夜间困意（Const, 0.6） | 睡眠时疲劳以 1.45/天 反解 |
| `GatherFood` | 是（食物格） | 饥饿（Survival, 2.5）、附近有食物（Linear, 1.0）、背包已有食物（Quad −0.9）、勤劳（+0.55） | **权重 2.5 必须显著高于木材/石料** |
| `GatherWood` | 是（森林格） | 木材储备充足（Quad −1.4）、基础需求（Const 0.56）、附近有森林（Linear 1.2）、勤劳 | `ReferenceStock = 30` |
| `GatherStone` | 是（石矿格） | 石料储备充足（Quad −1.0）、基础需求（Const 0.35）、附近有石矿（Linear 1.0）、勤劳 | `ReferenceStock = 20` |
| `Explore` | 是（远处随机格） | 基础倾向（Const 0.22）、精力（Linear 0.5）、离家距离（Quad −0.35） | 向外的扩散动力 |
| `Wander` | 是（近处随机格） | 基础倾向（Const 0.18）、精力（Linear 0.6） | 没有更迫切需求时的默认行为 |

**登记顺序即平局优先级**：生存类在前（Eat/Drink/Sleep/采集），漫游/探索在后。
平局时取先登记者，保证同一状态下决策唯一且确定。

### 5.1 性格如何进入权重（第 33 条）

M1 已接入**勤劳**：所有标记 `IsWork` 的动作都带一条
`ConsiderScore("勤劳性格", industriousness, industriousness, IndustriousnessWorkBonus)`。

M6 会接入其余五维（侵略性 → 攻击、善良 → 分享、勇敢 → 逃跑阈值、社交性 → 社交、
贪婪 → 囤积）。设计上不区分"性格直接改效用"与"性格改权重"——**都用 Consideration 表达**，
这样性格的影响同样可解释。

## 6. 选靶：不允许全知（第 19 条）

个体只搜索自己附近的区域。实现是**两级搜索**（`Actions/ActionSearch.cs`）：

1. 先用 chunk 聚合统计找出附近"确实有这种资源"的块，按距离由近到远；
2. 只对第一个命中的块内的格子做精确扫描。

### 6.1 为什么不直接扫半径内的每一格

半径 20 ⇒ 41×41 = 1681 格。100 个体 × 每次决策扫一遍，是这个模拟里最大的一笔开销。

用 chunk 统计把候选缩到 1~2 个块之后，扫描量下降一个数量级，
而**搜索范围反而更大**（chunk 半径 2 覆盖约 48×48 格）。

代价：找到的是"最近的且有该资源的块内的最近格子"，不一定全局最近。
这个近似是刻意的 —— 行为上看不出差别，性能差别很大。

### 6.2 选靶失败的处理

如果最优动作选不到目标（附近没资源），决策会**继续尝试次优动作**（最多 5 个）。
若全部失败，标记为 `Failed(NoTarget)`，并把下次决策时间提前到 1/4 间隔之后。

没有这层回退，个体会站在没有森林的地方一直"想砍树"。

## 7. 执行（`ActionSystem`）

```text
Condition（在效用函数里）
   → TargetSelection（选靶函数，可能失败）
   → Movement（A* 逐格前进，速度 MoveSpeedPerTick）
   → Execution（耗时动作：进食/饮水/睡眠/采集结算）
   → Result（Complete 或 Fail，写失败原因）
```

- **移动**用 `AStarPathfinder.FindNextStep` **每格重算**，而不是保存整条路径。
  理由：地形会变（玩家改地形、火灾烧毁），抱著旧路径会撞墙；
  每格重算一处 8 邻域搜索，代价可忽略。
- **耐心上限** `ActionPatienceTicks`（默认 900 tick）：超过就放弃，
  避免个体永远卡在一个到不了的目标上。失败原因写进 `FailReason`。
- 完成与失败都清空目标，并把 `NextDecisionTick` 设为 0（可立即重新决策）或延后。

## 8. 分批决策（第 73 条）

```text
phase = slot % batchCount
if (tick % batchCount != phase) skip;          // 每 tick 只处理 1/batchCount 的个体

batchCount 自适应：
  population ≤ TargetDecisionsPerTick  ⇒ 1（不分批，反应最灵敏）
  否则          ⇒ ceil(population / TargetDecisionsPerTick)，上限 64
```

**代价**：个体的信息会滞后几拍。因此每个动作在真正执行前都必须重新确认目标仍然有效
（`ActionSystem` 里的目标可走性检查与资源存量检查）。

## 9. 生存需求可以打断决策冷却（一次真实的踩坑）

决策冷却（`DecisionIntervalTicks`，默认 600 = 10 游戏小时）会阻止个体频繁改主意。
但如果**饥饿只能在这个窗口里被处理**，那么无论食物多充足、算法多正确，
一天最多也只能进食两次 —— 必然全体饿死。

实测现象极具误导性：**饮食统计在涨、随身食物有剩余、人还是在死**。

修法：`HasCriticalNeed` 检查（饥饿 ≥ 0.7 或干渴 ≥ 0.7 或健康 ≤ 0.35）可以绕过冷却。
阈值取 0.7 而不是更高：它明显高于"想要"的水平（0.2~0.4 由效用处理），
又低于开始掉血的 0.85，留出"还来得及"的缓冲。

**通用教训**：把"需求满足"与"决策频率"耦合在一起，会让系统在参数上不可行 ——
这类 bug 看起来像平衡问题，实际是可行性问题，而且极难从统计数字上看出来。

## 10. 可解释性输出（第 78 / 92 条）

每次决策都会保存 `UtilityBreakdown`（Top-N 个动作及其完整分解）到个体身上。
检查器直接渲染它，因此玩家能看到：

```text
当前动作：采集食物（效用 0.71）
────────────────────────────────
Eat          0.88   ← 被选中
  饥饿          0.82  survival → 0.97  × 2.00 = 1.94
  手上有食物      0.00  step(>=0.50) → 0.00  × 1.20 = 0.00   [被门挡住]
GatherFood   0.71
  饥饿          0.82  survival → 0.97  × 2.50 = 2.42
  附近有食物      1.00  linear → 1.00  × 1.00 = 1.00
  背包里已有食物   0.00  quadratic → 0.00  × -0.90 = 0.00
Sleep        0.39
  ...
```

这份输出的价值有两点：

1. **玩家**能理解"他为什么不去吃饭"（因为手上一粒粮食都没有）；
2. **开发者**排障时不需要猜权重 —— 每个数字都能追到来源。

## 11. 测试契约

| 测试 | 覆盖 |
|---|---|
| `UtilityRespondsToHunger` | 饥饿升高 ⇒ 采集食物效用必须升高 |
| `AllActionUtilitiesAreBounded` | 所有动作在所有需求极值下效用都在 [0,1] 且有限 |
| `CurvesAreMonotonicAndBounded` | 除常数外所有曲线单调不减（防止 InverseLogistic 方向写反） |
| `PathfindingAvoidsWater` / `FailsWhenUnreachable` / `IsDeterministic` / `DoesNotCutCorners` | 寻路正确性与确定性 |
| `GatheringMovesResourcesIntoInventory` | 采集确实把资源放进背包并扣减地面存量 |
| `EatingReducesHunger` | 进食确实降低饥饿 |
| `DigestsAreReproducibleWithAgents` | 有个体参与后状态摘要仍可复现 |
| `AgentsActuallyMove` | 移动链路真的在跑 |
| `BehaviourDiagnostics` / `SpawnSelectionDiagnostics` | 行为分布与选址诊断（排查"为什么都在挨饿"） |
