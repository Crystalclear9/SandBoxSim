# 01 — Game Design Document

> 本文件是项目的"宪法"。任何新增机制都必须能在这里找到它存在的理由；
> 找不到理由的机制不允许进入代码库（见 [11-MVP-Scope.md](11-MVP-Scope.md) 的准入检查表）。

---

## 1. 游戏愿景

一个**没有剧本、却能持续产生故事**的世界。

玩家做的事情始终只有两件：

1. **观察**这个世界在发生什么；
2. **改变条件**，然后继续观察。

世界里的城市、家庭、饥荒、迁徙、贸易、战争，都不是设计师写好的，而是若干简单规则
相互作用后的自然结果。玩家的乐趣来自"我改了条件，然后世界给了我一个我没预料到、
但完全说得通的答案"。

**一句话**：这是一个"哲学实验装置"形式的游戏 —— 你在里面做实验，世界负责给出结果。

---

## 2. 核心幻想（Core Fantasy）

玩家扮演的不是英雄，也不是国王，而是**世界的物理定律与气候本身**：

> "我不是在玩一个国家，我是在给一片土地、一群人、一套资源规则，然后看他们会变成什么。"

支撑这个幻想的具体体验：

| 体验 | 实现手段 |
|---|---|
| 我的干预会传播到我没预料到的地方 | 系统强耦合 + 因果链（见 §6） |
| 这些人是有个性的个体，不是棋子 | 性格影响效用函数 + 个人时间线与家庭（M6） |
| 世界有它自己的意志 | 全部结果由模拟产生，无脚本事件 |
| 我能理解为什么发生 | 可解释的效用分解 + 事件因果标签（见 10-DebugAndObservation） |
| 我的实验可以被复现 | 种子化随机 + 状态摘要（见 13-DeterminismAndSave） |

---

## 3. 核心游戏循环

```text
        ┌──────────────────────────────────────────────┐
        │                                              │
   观察世界 ──→ 发现现象/问题 ──→ 决定是否干预 ──→ 修改条件 │
        ↑                                              │
        │                                              ↓
        └────── 产生新结果 ←── 世界自行运行（Tick）──────┘
```

三角色循环（Observation → Intervention → Simulation → Emergence → Observation）要求三件事同时成立：

1. **可观察**：任何重要变化都能被玩家看见并被解释（否则玩家只是在看屏保）；
2. **可干预**：玩家有足够多的"条件旋钮"，且旋钮之间不是同义反复；
3. **可淹没**：模拟必须继续跑，玩家不按键世界也在变（否则玩家是在玩"手动推进器"）。

第一版的判定标准（第 93 条）：**玩家什么都不做，让世界运行 30 分钟，必须出现值得观察的变化。**

## 4. 玩家动机（Player Motivation）

| 动机 | 由什么满足 |
|---|---|
| **实验感** | 条件可任意组合、结果不可完全预测、实验可复现 |
| **养成感** | 从 3 个人到一个村庄，几十天内肉眼可见的成长 |
| **故事感** | 个体时间线 + 聚落历史 + 事件日志自然拼出叙事 |
| **观赏感** | 昼夜、天气、火灾、迁徙、人群在图上移动 |
| **掌控感** | 上帝工具可直接改变地形、气候、资源、规则 |
| **破坏欲** | 火灾、干旱、洪水、瘟疫（并进行灾后观察） |

关键：**"破坏欲"与"掌控感"最终都服务于"实验感"** —— 玩家烧掉森林不是为了发泄，
是为了看"木少之後这个世界会怎样"。

## 5. 涌现式玩法设计（Emergent Gameplay Design）

### 5.1 三条硬规则

1. **禁止结果导向的硬编码**：不允许 `CreateCity()`、`StartWar()`、`OnDay50_SpawnBandits()`。
   只允许改变条件与规则。
2. **每个系统必须至少连接两个已有系统**：孤立系统一律不做（见 §6 的连接度自检）。
3. **每个机制必须回答四个问题**（第 66 条）：
   - 它**读**哪些变量？（Input）
   - 它**改**哪些变量？（Output）
   - 它是否可能**自我放大**？（Positive Feedback）
   - 什么机制**限制**它？（Negative Feedback）

### 5.2 涌现是怎么长出来的：一条真实的传播链

```text
森林丰富
  ↓ 木材充足（ResourceSystem.Harvest）
居民容易建房（M3 BuildHouse）
  ↓ 住房增加（Housing）
人口增长（M4 出生条件 Housing > Population）
  ↓ 粮食需求上升（FoodDemand = f(Population)）
居民开垦农田（M4 Farm）
  ↓ 森林被砍伐（Farm 需要草地，伐木需要木材）
木材再生跟不上（Logistic 再生在低存量时更慢）
  ↓ 建房停滞 → 住房短缺 → 出生率下降
  ↓ 食物来源减少 → 饥饿上升
居民迁出（M7 Migration：U_migrate > 阈值）
  ↓ 新聚落诞生（M7 SettlementFounded）
两个聚落资源互补 → 贸易（M8）→ 或者 资源冲突 → 战争（M8）
```

这条链上**没有一行脚本**。"建立第二个村庄"不是任务，是系统运行的自然结果。

### 5.3 涌现性的体检标准

我们不靠感觉判断涌现性，而是靠可机测的指标（见 [12-Milestones.md](12-Milestones.md) 的验收表）：

- 100 天无人干预长跑中，必须出现：出生、死亡、建造、农田、迁出、第二聚落、火灾；
- 20 个不同 seed 批量长跑，不允许出现"什么都没发生"的世界；
- 玩家烧掉森林后，人口增速必须可测地下降（跨系统传播的最小证明）。

## 6. 系统连接度自检

新增系统前必须回答："它影响哪些已有系统？被哪些已有系统影响？"

```text
天气 ──→ 湿度 ──→ 作物产量 ──→ 食物供给 ──→ 饥饿 ──→ 人口 ──→ 迁移 ──→ 聚落规模
  │                    │                      ↑                        │
  └──→ 火灾风险 ──→ 森林/木材 ──→ 建造 ────────┘                        │
                                                        贸易/冲突 ←──────┘
```

孤立系统的典型反例（**禁止**）：一个"经济系统"只在自己的面板里算价格，
不读人口、不读资源、不影响职业选择。那样的系统对玩家来说只是装饰。

---

## 7. 胜负哲学（Win / Loss Philosophy）

**没有胜利条件，也没有失败条件。**

但世界可以有"结局"：

- 聚落全部灭亡 = 一个**实验结果**，不是 Game Over；
- 玩家随时可以重新播下几个人，让文明从废墟里再来一次；
- 死因必须可追溯（饿死 / 老死 / 火灾 / 战斗），这样"灭亡"才有叙事价值。

这是刻意的：一旦有输赢，玩家就会开始"最优解"，而最优解会杀死涌现性。

---

## 8. 沙盒哲学（Sandbox Philosophy）

| 原则 | 具体含义 |
|---|---|
| **条件是旋钮，结果是涌现** | 工具只写"上游变量"：地形、资源量、气候、规则倍率 |
| **没有剧情，只有历史** | 只记录发生了什么（EventLog），不预设该发生什么 |
| **没有隐藏规则** | 玩家能看到 NPC 的效用打分与死因（第 92 条 可解释性） |
| **可复现才有实验价值** | 同 seed 必同世界；改动可见、可回放、可对比 |
| **允许崩溃与周期** | 世界不应永远稳定；Boom / Bust / 迁移 / 崩溃 / 恢复是常态 |
| **不做"更多功能"，做"更有生命力"** | 优先级判据：是否增加涌现？是否增加玩家能动性？是否增加可观察性？ |

---

## 9. 玩家可用的"条件旋钮"总览（分阶段落地）

| 类别 | 工具 | 阶段 |
|---|---|---|
| 创造 | 放置居民 / 放置动物 / 催生森林 / 注入食物与资源 | M0 部分（地形/资源）、M1（人） |
| 地形 | 抬升 / 下沉 / 创造河流 / 创造山脉 / 创造/移除水域 | M0 ✅ |
| 资源 | 食物 / 木材 / 石头 / 铁 | M0 ✅ |
| 恩惠 | 提升肥沃度 / 提升出生率 / 治愈 / 提升产量 | M2–M5 |
| 灾害 | 火灾 / 闪电 / 洪水 / 干旱 / 瘟疫 / 陨石 | M0 部分（干旱/降雨）、M5 |
| 规则 | 禁止战争 / 高出生率 / 快速衰老 / 不死 / 双倍资源 / 和平模式 | M5 |

**永远不会有**：创建城市 / 发动战争 / 让人变富 / 指定某人当领袖。

## 10. 视觉设计原则（第一阶段）

不投入美术。用颜色与形状把**信息**表达清楚：

| 元素 | 表现 |
|---|---|
| 地形 | 纯色块（草绿 / 林深绿 / 水蓝 / 山灰 / 沙褐 / 农田金黄） |
| 资源丰度 | 用**明度**表达（森林被砍秃会变黄褐，矿被挖空会变暗灰） |
| 居民 | 小字符或色点（M1） |
| 建筑 | 符号（M3） |
| 火灾 | 高饱和橙黄闪烁 |
| 热力图 | 统一蓝→绿→红渐变 |

配色统一在 `Console/Render/Palette.cs`，**TUI 与 PNG 快照共用同一套映射**，
保证"屏幕上看到的"和"报告里的图"一致（避免观察结论互相矛盾）。

## 11. 观察价值（Observation Value）优先于内容量

模拟游戏最常见、也最致命的失败不是"内容不够"，而是**玩家看不懂发生了什么**。

因此本项目的实现顺序刻意是：

> 先把世界跑起来 → 再把"为什么"暴露出来 → 最后才加内容。
> （见 10-DebugAndObservation.md 与 12-Milestones.md 的 M0 为何先做空间索引与摘要）

具体做法：

- 每个重大事件都带**因果标签**（`WorldEvent.Cause`）；
- NPC 的决策能显示**效用分解**（每项考虑的名字 / 输入值 / 曲线 / 权重 / 贡献）；
- 死亡必须写**死因**；
- 世界状态可导出**快照 PNG**，让"我看到了什么"可以被别人复核；
- 统计曲线覆盖人口、食物、木材、森林、湿度、紧张度。

---

## 12. 三条最重要的判据（贴在墙上）

1. **玩家什么都不做，30 分钟内有值得观察的变化吗？** 没有 → 系统还不够有机。
2. **玩家改变一个条件，后果能否通过多个系统传播出意料之外但合理的结果？** 不能 → 耦合太弱。
3. **玩家能知道"为什么"吗？** 不能 → 观察体系有缺口，比缺功能更严重。
