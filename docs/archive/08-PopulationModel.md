# 08 — 人口模型

本文件规定"人从哪来、为什么死、人口为什么会涨落"。
M2 只实装了**死亡**（出生在 M4），但先写清整体设计，避免之后为了加出生而返工。

对应源码：`Systems/NeedsSystem.cs`、`Agents/AgentStore.cs`、`SimulationStats.cs`。

---

## 1. 生命历程（LifeStage）

| 阶段 | 年龄（游戏日） | 参数 | 行为差异 |
|---|---|---|---|
| `Child` | 0 – 16 | `AdulthoodDays` | 不独立迁移（跟着家庭）；M4 起不工作 |
| `Adult` | 16 – 55 | `ElderDays` | 全部行为可用 |
| `Elder` | 55 – 90 | `MaxLifespanDays` | 有老年死亡概率 |
| `Dead` | > 90 或非自然死亡 | — | 槽位进入复用池 |

**为什么阶段阈值是数据而不是硬编码**：不同世界（丰饶/严酷）应该有不同的人口结构，
而"多少岁算成年"是最容易被玩家调的一类参数。

---

## 2. 需求（Needs）

四个需求全部归一化到 [0,1]，**0 = 完全满足，1 = 极端**。

| 需求 | 默认速率 | 恢复方式 | 触发阈值 |
|---|---|---|---|
| `Hunger` | `HungerPerDay` = 1.0 | 进食（每 tick 0.6 食物 → 0.09 饥饿恢复） | 0.7 打断决策冷却；0.85 开始掉血 |
| `Fatigue` | `FatiguePerDay` = 1.15（夜里 ×1.25） | 睡眠（`SleepRecoveryPerDay` = 1.45） | 由效用函数处理（无硬阈值） |
| `Thirst` | `ThirstPerDay` = 1.5 | 饮水（临水格） | 0.7 打断冷却；0.9 开始掉血 |
| `Social` | `SocialPerDay` = 0.5 | M6 的社交/家庭 | — |
| `Health` | — | `HealthRecoveryPerDay` = 0.1（不饥不渴时） | ≤ 0.35 打断冷却；≤ 0 死亡 |

### 2.1 "打断决策冷却"是什么，为什么必须有

决策冷却（`DecisionIntervalTicks` = 600 = 10 游戏小时）阻止个体频繁改主意。
但如果**饥饿只能在这个窗口里被处理**，那么无论食物多充足，一天最多也只能进食两次 ——
在数学上不可行。

实测现象极具误导性：**饮食统计在涨、随身食物有剩余、人还是在死**。

因此 `AiSystem` 里有 `HasCriticalNeed`：饥饿 ≥ 0.7 或干渴 ≥ 0.7 或健康 ≤ 0.35 时绕过冷却。
阈值取 0.7 是刻意的：它明显高于"想要"的水平（0.2~0.4 由效用函数处理），
又低于开始掉血的 0.85，留出一段"还来得及"的缓冲。

## 3. 死亡（M2 实装）

### 3.1 死因枚举与判定

| `DeathCause` | 判定条件 | 严重度 |
|---|---|---|
| `Starvation` | `Hunger ≥ StarvationDamageThreshold(0.85)` 时按 `StarvationDamagePerDay(0.25)` 掉血 | 常见 |
| `Dehydration` | `Thirst ≥ DehydrationDamageThreshold(0.9)` 时按 `DehydrationDamagePerDay(0.45)` 掉血 | 较少见（走太远） |
| `OldAge` | 年龄 ≥ `ElderDays` 时按 `ElderMortalityPerDay(0.012)` 判定；或年龄 ≥ `MaxLifespanDays` 直接死 | 长跑必然 |
| `Violence` / `Fire` / `Disease` / `Accident` | M5–M8 | — |

### 3.2 死亡路径必须唯一

所有死亡都必须经过 `NeedsSystem.Kill(store, slot, cause, tick)`。
它做四件事：写存活标志、写死因与死亡时刻、累加分类计数、登记 `DeathRecord`。

**为什么要 `DeathRecord`**：上层（`Simulation.RecordDeathsFromNeeds`）需要把死亡写进事件日志
与统计。如果让上层"自己扫一遍找出谁刚死了"，就变成 O(容量) 的每 tick 扫描 ——
而 `DeathsThisTick` 计数必须**在每 tick 开始时清零**（它是"本 tick 的明细"），
事后再看永远是 0。这就是为什么明细要显式传出来。

> 这个坑当时是这样暴露的：测试用 `Assert.False(IsSlotAlive(...))` 通过，
> 但用 `DeathsByCause` 断言失败 —— 因为后者是累计值，前者是每 tick 值。
> 判据用错比逻辑写错更难发现。

### 3.3 死亡后的数据保留

`MarkDead` **不清理**槽位里的数据（位置、年龄、库存都留着），只改存活标志与代次。
理由：死亡时刻的位置/年龄/死因还需要被事件日志与报告读到。
清理会让"他死在哪"变成一个查不到的信息。

代次 +1 则保证**旧的 `AgentRef` 立刻失效**，防止槽位复用后"看错人"。

## 4. 出生（M4 已实装）

模型与当初的规划一致，但**实现时对两处语义做了明确判断**，
这两处都踩过坑，值得单独写清楚：

```text
birthChancePerDay = BaseChancePerDay
                  × max(食物充足度, foodFactorFloor)   // 吃不饱就不生
                  × 住房充足度（0 或 1，**硬门**）      // 没地方住就不生（第 37 条）
                  × (0.5 + 0.5 × 双方健康度)           // 虚弱显著降低生育
                  × (1 − clamp01(人口 / 床位) × 人口压力强度)   // 接近承载上限时下降
```

### 4.1 住房是**门**，健康是**因子** —— 两者不能混

| | 语义 | 形式 | 误做成另一种会怎样 |
|---|---|---|---|
| 住房 | **门**（gate） | 0 或 1，乘性零因子 | 若做成加成，则"床位为 0 时仍有出生"，住房约束形同虚设 ⇒ M3 的建造系统失去意义 |
| 健康 | **因子**（factor） | 连续、有下限 | 若做成资格，则某个体一旦暂时虚弱，**伴侣关系会被清理规则拆掉**（实测 40 人世界配对数 5 天内从 16 对崩到 3 对，出生数恒为 0） |

第二条是真实踩到的设计错误。它的症状很有欺骗性：
看起来像"出生概率调得太低"，实际是**关系被反复拆散**。
**把因子误做成门的典型症状是"某个机制完全失效"，而不是"数值偏小"。**

### 4.2 为什么健康因子是 `0.5 + 0.5 × health` 而不是裸 `health`

因为慢性亚健康（例如长期缺水导致健康停在 0.4）会让裸 `health` 把出生率压到 4 成，
而且**永远恢复不了**。实测 40 人世界的出生率只有约 0.2/天，而死亡约 0.44/天 ⇒ 必然灭绝。
健康的作用应当是"明显虚弱时显著降低生育"，而不是"只要不是满血就几乎不能生" ——
真实人口学里的形状也是正相关而非线性归零。

### 4.3 食物口径（调试时最容易搞错的一点）

出生读的是"**当下真的能吃到**的食物"：
`共享库存 + 地面物资堆 + 各人随身`。**不含**地里还没长出来的存量。

这带来一个调试陷阱：`InterveneAddResource` 写的是**格子存量**，
它必须先被采集才进入"可支配"口径。用"多撒食物"来制造对照实验的差异是**无效的**
（实测两组出生数完全相同：17 vs 17）。要制造差异应当改 `foodPerCapitaTarget`
（食物因子的分母），它直接、确定、且可隔离。

### 4.4 家庭雏形（M4 的临时形态）

M4 **没有**关系系统（那是 M6）。伴侣用"同住 / 同地"近似：

* 清理失效关系（伴侣已死或已不是合格生育者）；
* 优先与**同住所**的合格个体配对，其次才是 `pairRadius` 内最近的；
* 全部按**槽位升序**遍历 ⇒ 结果与遍历顺序无关（确定性要求）。

配对结果、生育次数与上次生育时刻都进 `StateHash` 与存档 ——
判据仍然是"它会不会影响未来的行为"。

### 4.5 初始人口的年龄必须散布

`InterveneSpawnHumans` 原先给所有人 `ageDays: 0`，也就是**同一天出生**。
于是他们会在同一天进入老年、又在同一天撞上 90 天寿命上限 ——
实测 100 天时曲线看着不错（40 → 47），但 90–100 天之间**整批人同时老死**，
200 天必然归零。

**这不是"平衡没调好"，是初始条件本身不成立**：没有任何真实聚落的成员年龄完全一致。
现在年龄散布在 `[adulthoodDays, elderDays)`，也就都是生育年龄 ——
与"放一批定居者"的语义一致。

## 5. 人口与其它系统的反馈环

| 环 | 类型 | 链路 | 阻尼 |
|---|---|---|---|
| 人口 → 消耗 → 稀缺 | 负 | 人口↑ → 消耗↑ → 局部资源↓ → 采集效率↓ | **主要阻尼** |
| 人口 → 拥挤 → 迁移 | 负 | 人口↑ → chunk 拥挤↑ → 迁移意愿↑ → 人口分散 | 迁移冷却（8 天） |
| 人口 → 采集 → 枯竭 | 负 | 人口↑ → 采集↑ → 资源被采绝（不可逆） | Logistic 再生的存量因子 |
| 人口 → 猎杀 → 猎物↓ | 负 | 人口↑ → 猎杀↑ → 动物↓ → 打猎收益↓ | 动物繁殖率与容量 |
| 住房 → 出生 → 劳动力 | 正 | 木材↑ → 住房↑ → 出生↑ → 劳动力↑ → 木材↑ | 木材再生速度（M3/M4） |

### 5.1 M2 的一个硬事实：**没有出生 ⇒ 长跑必然灭绝**（M4 已解决）

40 人、100 天（**M4 之前**）：
- 0–40 天：人口稳定（资源充足，采集与捕猎足够）；
- 40–70 天：开始出现衰老死亡（55 天进入老年）；
- 70–150 天：人口单调下降到 0（90 天硬性寿命上限）。

实测 150 天：**38 例衰老、2 例脱水、0 例饥饿**。

**M4 之后，同一配置下人口稳定在 46 人（床位 46/46），200 天不灭绝也不爆炸，
死因只剩自然衰老。** 从"必然灭绝"到"长期稳定"是 M4 的全部意义 ——
在那之前，前面几个里程碑做出来的经济、建造与迁徙最终都走向同一个结局。

这不是 bug，而是**设计上的空缺**：它正是 M4 "出生系统"的动机。
在文档里明确写出这件事，比让它以"人口莫名归零"的形式被误解要好得多。

## 6. 统计口径

| 指标 | 采样 | 说明 |
|---|---|---|
| `PopulationCount` | 每 tick 从 `AgentStore.LiveCount` 同步 | 不是"每天算一次"，因为它被用于 UI |
| `TotalBorn` / `TotalDied` | 累计 | 死亡在 `MarkDead` 里 +1 |
| `DeathsByCause[]` | 累计（16 项） | **累计值**，不要与 `DeathsThisTick` 混用 |
| `Births` / `Migrations` | 累计 | 进日报（出生 M4 才有） |
| `AverageHunger` / `AverageFatigue` | 即时查询 | 只在面板/诊断里用，不进每 tick |
| `PeakPopulation` | 累计最大值 | 报告里用于说明"这个世界的规模" |

日报里的 `Population` 用 `BuildDailySample` 快照，**不进每 tick 热路径**。

## 7. 测试契约

| 测试 | 覆盖 |
|---|---|
| `NeedsAccumulate` | 需求随时间累积 |
| `StarvationKillsWithCorrectCause` | 饥饿致死且死因正确（**分两步**：先测纯生理链路，再测完整管线） |
| `StoreLifecycle` | 死亡后旧引用立刻失效 |
| `NamesAreStableAndUnique` | 名字稳定且不重复 |
| `EveryoneDecidesEventually` | 分批决策不会让谁被永久跳过 |

### 7.1 为什么"饿死"测试要分两步

第一版直接跑 `sim.Tick(3000)` 然后断言"他应该饿死" —— 结果**没有死**。
原因不是 bug，而是"需求系统 + AI"整体在正常工作：他自己跑去采集食物吃饱了。

也就是说：想断言"饿会致死"，必须把因果链缩到**只剩饥饿这一个环节**
（直接驱动 `NeedsSystem.TickNeeds`），否则测试其实是在断言"AI 不够聪明"，
而那是另一回事，并且会随调参随机失效。

第二步再验证"通过完整管线也能饿死"：把饥饿速率调到远超采集能力（200/天），
世界再怎么丰饶也来不及 —— 这样断言就是稳定的。
