# 03 — Simulation Architecture

本文件回答一个问题：**世界每时每刻在按什么节奏、按什么顺序推进？**

这是模拟项目里最容易出错的地方：所有系统都挤在"每帧执行"里，
结果要么性能爆炸，要么行为随帧率变化（同一 seed 在不同机器上跑出不同世界）。

---

## 1. 时间基准（唯一时钟）

| 概念 | 取值 | 说明 |
|---|---|---|
| 1 Tick | 1 游戏分钟 | 所有系统的调度单位 |
| 1 游戏小时 | 60 Tick | 天气、再生、统计 |
| 1 游戏天 | 1440 Tick（24 小时） | 年龄、出生、死亡、迁移 |
| 1× 速度 | 10 Tick/秒 | 默认推进率 |
| 倍速档 | 0 / 1 / 2 / 4 / 8 | 只改"每秒多少 tick" |

**时钟只有一个**：`World.Calendar.Tick`（`Simulation.Clock` 是它的别名）。
模拟内核里禁止出现 `DateTime.Now`、`Stopwatch`、`Environment.TickCount`。

> 唯一的例外在 `Console/GameLoop.cs`：它用 `Stopwatch` 控制**渲染帧率与每秒推进多少 tick**。
> 这是表现层的职责，不进入 Core，也不参与状态摘要。

## 2. Tick 管线（顺序即契约）

```text
GameLoop（表现层）
  └─ 按 60 FPS 采样 → 计算本帧应推进几步 → 调用 Simulation.Tick(steps)

Simulation.Tick(steps)   // steps 通常 0~40
  for (i = 0; i < steps; i++) {
      1. Calendar.Advance(1)                     // 时间 +1 分钟
      2. Actions.Tick(tick)                      // 移动 / 执行 / 结算（必须最先）
      3. Needs.TickNeeds(...)                    // 需求累积 + 掉血 + 死亡判定
      4. RecordDeathsFromNeeds(tick)             // 死亡写进事件日志与统计
      5. Ai.Tick(tick, isNight)                  // 分批决策（基于最新的需求）
      6. if (Tick % 10   == 0) TickFast()        // 施工/生产/火势（M3+）
      7. if (Tick % 60   == 0) TickHourInternal()
           ├─ WeatherTick()                      // 天气 → 写 Tile 湿度/温度
           ├─ ResourceSystem.Regenerate(1/24天)   // Logistic 再生
           └─ TickHour()                         // 各系统小时级逻辑（M4+）
      8. if (Tick % 1440 == 0) TickDayInternal()
           ├─ ResourceSystem.Regenerate(1天)      // 若配置为按天再生
           ├─ TickDay()                          // 年龄/老年死亡/分批数重算
           └─ Stats.RecordDay(BuildDailySample())
      9. World.RefreshSpatialIndex()             // 所有写盘者都已写完，这里统一刷新
     10. PopulationCount = Agents.LiveCount
     11. if (Tick % 64 == 0 && AssertInvariants) ValidateInvariants()
  }
```

### 2.1 个体层三步的顺序是 M1 最关键的契约

**动作 → 需求 → 决策**，任何交换都会让行为整体错位：

| 交换 | 后果 |
|---|---|
| 决策 → 动作 | 个体在"需求还没更新"时就决定，反应慢一拍 |
| 需求 → 决策 → 动作 | 动作在这一 tick 不推进，移动速度实际减半 |
| 动作 → 决策 → 需求 | 决策依据的是上一 tick 的需求，饥饿临界点判定漂移 |

这类错误不会崩、不会报 NaN，只表现为"行为看起来有点迟钝"，
因此必须写进文档并由测试锁定（`HourEventsFireOnce`、`DailySampleIsRecorded`）。

### 2.2 为什么顺序不能配置

任何一个相邻步骤交换，世界演化都会变：

- 若**先刷新空间索引再改天气**：AI 会基于过期的湿度/资源做决策；
- 若**先算统计再执行每日逻辑**：曲线整体滞后一天，玩家看到的因果会对不上；
- 若**先做出生再算食物**：新生儿在第一天的口粮不计入，饥荒会被低估。

因此顺序是写死的常量，并由测试锁定（`WorldTests.HourEventsFireOnce`、
`WorldTests.DailySampleIsRecorded`、`WorldTests.TickAdvancesCalendar`）。

### 2.2 为什么空间索引刷新放在最后一步

空间索引是**缓存**，真相在 `Tile[]` 里。把刷新放在"所有可能改格子的系统都跑完"之后，
可以保证：

1. 每 tick 最多重算一次（而不是每个写者各自触发一次）；
2. AI 在同一 tick 内看到的聚合数据是自洽的（不会出现"半旧半新"的 chunk 统计）。

## 3. 各系统更新频率总表

| 系统 | 频率 | 预算（每 tick） | 备注 |
|---|---|---|---|
| 时钟推进 | 每 tick | O(1) | — |
| 空间索引刷新 | 每 tick（仅脏 chunk） | O(脏格子数) | 通常 0~100 格 |
| 天气 | 每小时 | O(地图格子数) | 100×100 = 1 万格写入，需注意此处的常数 |
| 资源再生 | 每小时 | O(所有带资源节点的格子) | 同上量级；不可再生资源直接跳过 |
| 统计采样 | 每天 | O(地图格子数) | 只在日边界发生 |
| 状态摘要 | 手动 / 每 1440 tick（可配） | O(全状态) | 用于确定性验收，不进热路径 |
| **Agent 需求累积** | 每 tick | O(agentCount) | 纯算术，很快 |
| **Agent 动作推进** | 每 tick | O(活跃动作数) | 空闲个体跳过 |
| **Agent 决策** | 每 tick，**分批** | O(TargetDecisionsPerTick) | 有硬上界（默认 12/12 人），见 [14-Performance](14-Performance.md) |
| **寻路** | 决策时发生 | O(格子数 log 格子数)，带 4000 节点上限 | 唯一可能昂贵的操作 |
| 年龄与老年死亡 | 每天 | O(agentCount) | — |
| 建造与生产（M3） | 每 10 tick | O(在建/生产中建筑数） | — |
| 火灾蔓延（M5） | 每 10 tick | O(燃烧格子数) | 燃烧总数有天然上限 |
| 聚落评估（M4/M7） | 每小时 / 每天 | O(聚落数 × 成员数） | — |

**实测数据（M1，Windows / .NET 8 / Debug 构建 / 100×100 地图 / 40 个体）**：

| 场景 | 规模 | 实测 |
|---|---|---|
| 无个体长跑 | 100 天 | ≈ 73,000 tick/秒 |
| 40 个体 + AI | 100 天（144,000 tick） | **≈ 59,000 tick/秒**（2.44 秒） |
| 40 个体 + AI + PNG 快照 | 100 天 + 5 张快照 | ≈ 42,000 tick/秒 |
| 确定性校验（带个体） | 30 天 × 2 遍 | 每遍 **0.78 秒** |
| 6 seed × 60 天批量（带个体） | 6 × 86,400 tick | 平均 **1.65 秒/局** |
| 全部测试 | 115 个用例 | **1.5 秒** |

换算：1× 速度 = 10 tick/秒 ⇒ 100 天在 1× 下需要 4 小时游戏时间，
而模拟只花 2.44 秒（约 **5,900 倍实时**）。**当前性能余量约三个数量级。**

完整数据与优化取舍见 [14-Performance.md](14-Performance.md)。

### 3.1 M0 的"空世界基线"（重要参考值）

M0 还没有居民，因此资源**只有再生、没有消耗**。100 天无人干预的实测结果：

| 指标 | 起始 | 第 100 天 | 说明 |
|---|---|---|---|
| 食物存量 | 46,175 | 73,608 | 逼近容量（Logistic 再生） |
| 木材存量 | 82,099 | 94,056 | 同上 |
| 森林格数 | 963 | 963 | 无人砍伐 ⇒ 不变 |
| 平均湿度 | 0.73 | ≈1.0 | 湿润自强化被 clamp 兜住 |
| 资源紧张度 | 0.29 | 0.03 | 因为存量在涨 |

**这个基线有两个用途**：

1. **它是"世界没有生命"的证据**。森林格数不变、地平线不变、事件只有 1 条 ——
   这正是第 93 条判据（"什么都不做的 30 分钟里有没有值得观察的变化"）在 M0 的答案：
   **没有**。而这恰恰说明 M1 之后加进来的东西是不是真的起作用了。
2. **它是后续里程碑的对照组**。当 M4 的农业与人口接进来之后，同样的 100 天里
   森林格数必须下降、食物曲线必须出现波动（而不是单调上升）、事件数必须从 1 涨到几十。
   如果没变，说明新系统没有真正接入因果链 —— 这是最便宜的"接线检查"。

因此 `runs/` 的产物虽然默认不入库，但**每次里程碑验收都要跑一遍这条基线并存档**。

## 4. 渲染与模拟解耦（第 82 条）

```text
渲染：60 FPS 固定目标
  ├─ RefreshSize()        // 终端尺寸变化
  ├─ 采样输入（非阻塞）
  ├─ 计算本帧应推进的 tick 数 = TPS × 倍速 ÷ 实际帧率
  ├─ sim.Tick(ticks)      // ← 模拟只在这里被推进
  └─ 画一整帧 → 单次 flush
```

关键点：

1. **倍速不影响 tick 语义**。×8 只是"每秒推 80 个 tick"，不是"每个 tick 走 8 倍时间"。
   这保证了不同倍速下世界演化**完全一致**（同 seed 下 1× 跑 100 天 == 8× 跑 100 天）。
2. **单帧追赶上限**（`MaxCatchUpTicksPerFrame = 40`）：卡顿后不会一次性补上千 tick，
   否则会看到"世界突然跳变"，而且会让长跑的时间分配失控。
3. **模拟绝不阻塞在输入上**：`Console.KeyAvailable` 轮询，没有输入就继续推进时间。
4. **一帧只写一次终端**：整帧先在 `RenderBuffer` 里画好，再一次性输出。
   逐格输出在 Windows Terminal 下会导致明显闪烁与极高 CPU。

## 5. 性能设计原则（第 73 / 74 条）

### 5.1 绝不 "Every NPC × Every Frame"

```text
错误做法：for each agent: for each tile in searchRadius: ...
          → 100 agent × 500 格 × 60 帧 = 每秒 300 万次格查询

正确做法（M1 实装）：
  phase = agentId % batchCount            // 分批（交错更新）
  if (tick % batchCount != phase) skip;   // 每 tick 只让 1/batchCount 的 agent 决策
  → 单 tick 决策数有上界；每个 agent 的决策间隔约 batchCount 个 tick
```

**分批的代价**：agent 的信息会滞后最多 `batchCount` 个 tick。
所有系统都必须容忍这一点（"他上一拍还在往已经不存在的森林走"），
这也是为什么决策接口设计成"每次决策时重查目标有效性"。

### 5.2 空间索引（第 74 条）

```text
World.Tiles（真相，行主序数组）
   ↓ 被聚合
ChunkGrid（16×16 的块，缓存 16 个统计量）
   ├─ 森林/水域/山地/草地/农田 格数
   ├─ 可通行/可建造 格数
   ├─ 木材/食物/石/铁 总量
   ├─ 肥沃度/湿度/温度/植被 求和（除以 CellCount 得均值）
   └─ 燃烧格数
```

AI 查"附近有没有吃的"只需读 3×3 = 9 个 chunk 的聚合值（O(1)），
只有真正挑具体格子时才对少量候选格求值。

**维护方式**：脏标记 + 惰性重算。任何 Tile 写入都会 `MarkDirty`，
`Simulation` 每 tick 调一次 `Refresh`，只重算脏块（通常是 0~个位数）。

### 5.3 数据结构选择

| 场景 | 选择 | 理由 |
|---|---|---|
| Tile 存储 | `Tile[]` 值类型数组 | 缓存友好、可整体拷贝做摘要、无 GC 压力 |
| Chunk 统计 | `double[16]` 定长数组 | 避免为"某种资源"新增字段时改结构布局 |
| 事件日志 | 环形缓冲数组 | 长期运行不无限吃内存（保留最近 2 万条） |
| 统计曲线 | `List<DailySample>`（每天一条） | 一天一条，100 年也只有 3.6 万条 |
| 资源字典 | **不使用字典** | 字典迭代顺序不确定，会破坏可复现性 |
| 库存 | 具名字段结构体 | 固定 4 种资源，字段访问比数组索引更可读 |

## 6. 多线程与并行

**当前阶段：单线程**。理由：

1. 并行会让"确定性"变得非常难（浮点归约顺序、任务调度顺序都会影响结果）；
2. M0–M5 的规模（数百 agent、1 万格）在单线程下还有 1~2 个数量级余量；
3. 项目的第一原则是"可复现"，而不是"极限吞吐"。

**未来若需要并行**，唯一允许的方式是**只读并行**：

- 天气/再生按行分块并行（每块只写自己的格子，写入不重叠）；
- 决策阶段并行评估各 agent 的效用（每个 agent 独立），但**决策结果的写回必须串行按索引顺序**；
- 禁止对同一个 `ResourceSystem` 统计计数做并行写入（需要原子或分桶归约）。

在这之前，先做分批与空间索引 —— 它们带来的收益远大于并行，且不牺牲确定性。

## 7. 确定性契约（实现约束）

写任何模拟逻辑时，以下行为都是**禁止**的：

| 禁止 | 原因 | 替代 |
|---|---|---|
| `System.Random` | 运行时实现可能变化，不可复现 | `SimRandom.Get(RngStream.X)` |
| `DateTime.Now` / `Stopwatch` | 结果依赖真实时间 | `World.Calendar.Tick` |
| 遍历 `Dictionary` / `HashSet` | 迭代顺序不保证 | 索引数组 / 有序列表 |
| `float.ToString()` 参与逻辑判定 | 文化设置影响格式 | 直接用数值比较 |
| `Environment.TickCount` | 同上 | 同上 |
| 依赖 `object.GetHashCode()` | .NET 会加随机化种子 | `Hash64` |
| 在渲染里改模拟状态 | 破坏"模拟只由 tick 推进" | 走 `Intervene*` 接口 |

对应测试：`WorldTests.StateDigestIsReproducible`（同 seed 两跑一致）、
`WorldTests.StateDigestDiffersBySeed`（种子真的生效）、
`RandomTests.DrawingFromOneStreamDoesNotDisturbOthers`（分流不互相干扰）、
以及 `--digest` 模式的端到端校验。

## 8. 架构演进路线（避免过早复杂化）

| 阶段 | Tick 架构 | 不做的事 |
|---|---|---|
| M0–M2 | 单线程，分批决策，chunk 索引 | 不做 ECS 框架、不做作业系统、不做序列化框架 |
| M3–M5 | 增加 FastTick（施工/生产/火） | 不做空间二叉树（chunk 足够） |
| M6–M8 | 每小时/每天的分层结算（聚落、贸易） | 不做多线程 |
| M9+ | 按实测决定是否并行只读阶段 | 不在没有基线的情况下优化 |

> 原则：**先让世界活着，再让它跑得快。** 一个跑得很快但什么都不发生的世界毫无价值。
