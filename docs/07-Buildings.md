# 07 — 建筑（M3）

本文件规定建筑的**造价、作用、选址规则与生命周期**，以及"建筑如何改变世界"。

对应源码：`World/BuildingStore.cs`（配方 + 存储）、`Systems/BuildingSystem.cs`（施工推进）、
`Systems/Actions/BuildActions.cs`（效用与选址）、`World/StorageStore.cs`（共享库存）。

---

## 1. M3 的设计目标（一句话）

**让攒下来的物资变成改变地形的能力。**

M2 结束时，世界已经有了"物资在空间上堆积"的现象，但那些东西没有任何用途 ——
玩家看到的是一群人在囤积。M3 给它们一个去处，并且让"建造"成为一条完整的循环：

```text
采集（M2） → 存放（M2） → 建造（M3） → 住房/仓库（M3） → 更多人口/更高效搬运（M4）
```

## 2. 配方表（`BuildingRegistry`）

| 建筑 | 木材 | 石料 | 施工点数 | 作用 | 允许地形 |
|---|---|---|---|---|---|
| **住房 House** | 20 | 0 | 200 | 提供 2 个床位 | 草地 / 森林 / 沙地 |
| **仓库 Storage** | 40 | 10 | 300 | 每种资源 600 的共享容量 | 草地 / 森林 / 沙地 |
| **农田 Farm** | 10 | 0 | 150 | 开垦后地表变 `Farmland`（产出在 M4） | 仅草地，**必须临水** |
| **矿场 Mine** | 15 | 5 | 250 | 山地开采（效率加成在 M4） | 仅山地 |

### 2.1 数值设计原则（第 88 条：什么都不给免费）

- 一间房子 ≈ 2.5 次采伐（每次 8 木材）⇒ 一天以内能盖起来，但不至于随手就盖；
- **仓库比住房贵**（40 木 + 10 石）：它带来的是"共享"这种结构性收益，不是个人福利；
- **石料只用在仓库上**：让"采石"在 M3 就有明确用途，而不是纯占位；
- 施工点数对应"约 2~3 天的工期"（`WorkPerFastTick = 8` ⇒ 200 点 ≈ 25 次 FastTick ≈ 250 tick)。

### 2.2 允许地形为什么是**显式列举**

山地在规则表里是"可走 + 可建造"的（矿场需要它），
因此**不能**用"可建造"当住房的判据 —— 那会得到"房子盖在山顶上"。

```csharp
TerrainKind[] flat     = { Grass, Forest, Sand };   // 住房、仓库
TerrainKind[] mountain = { Mountain };              // 矿场
TerrainKind[] farm     = { Grass };                 // 农田
```

这类"规则表里的某个格子其实是给别的用途的"情况，只能用显式列举表达意图。
（实测：第一版用"可建造"当判据，测试立刻发现房子能建在山地上。）

## 3. 选址规则（第 31 条）

`BuildingStore.CanPlaceAt` 是**唯一的选址规则入口** —— 动作层、UI、玩家工具、测试都必须走它。
否则会出现"玩家能建而 AI 不能建"这类不一致，而且很难发现。

| 规则 | 判据 | 理由 |
|---|---|---|
| 在边界内 | `IsInBounds` | — |
| 未被占用 | `Tile.BuildingId == 0` | 一格一个建筑 |
| 可走 | `Tile.Walkable` | 不能建在深水里 |
| 不是已有功能区 | 排除 `Road` / `Farmland` | 不要把已有功能覆盖掉 |
| 地形允许 | `recipe.AllowsTerrain` | 见 §2.2 |
| 农田临水 | `HasWaterAccess`（四邻有水） | 灌溉是农田的硬前提 |

`BuildAction.SelectSite` 在此之上加三条**行为层**规则：

1. **离自己近**：以自己为圆心按环由近到远扫描（半径 `SiteSearchRadius = 14`）；
2. **住房离水 1~6 格**：够用但不必占着河边（河边的好地应该留给农田）；
3. **不占用别人站着的格子**：`AgentStore.IsSlotOccupied(exceptSlot, x, y)` ——
   注意要排除**选址者自己**，否则"脚下这一格"永远算被占用，而它往往是最好的位置。

> 选址与"值不值得建"共用同一份信息（同一个 `SelectSite` 调用同时给出位置与距离），
> 因此不会出现"效用函数觉得近、动作却觉得远"这种自相矛盾。

## 4. 施工（`BuildingSystem`）

```text
动作层：走到工地 → 扣料 → 放下工地（Planned → UnderConstruction）→ 离开
系统层：每 10 tick（FastTick）推进 WorkPerFastTick 点施工进度
        → 累计到 BuildWorkTicks ⇒ MarkComplete（写事件、汇总量、农田改地形）
```

### 4.1 为什么"开工之后工人就走了"

这是 M3 最重要的一个设计决定。让个体一直守在工地上会有三个问题：

1. **经济会被压垮**：一个人至少要不吃不喝好几天才能盖完一间房，
   40 个人里只要有 3 个在建房，食物产出就会明显下降；
2. **现实里也不是这样**：工地是"开工之后按进度推进"的；
3. **它把"劳动力"与"工期"解耦**：工期由系统推进，
   于是"劳动力投入"可以成为**另一个**可调维度（M4 的建造速度加成）。

### 4.2 为什么施工要跨多个 tick

- 它是**可见的过程**（玩家能看到工地逐步成型，而不是凭空出现）；
- 它给"施工被打断"留出空间（M5 的火灾、M8 的战争都会打断工地）；
- 它让"建造需要时间"在数据上成立，而不是一句设定。

### 4.3 事务性（关键约束）

`BuildingSystem.TryStartBuilding` **要么"扣料 + 放下工地"都成功，要么什么都不变**。

```text
1. 检查配方存在
2. 检查位置可建造（CanPlaceAt）
3. 检查材料足够（随身 + 附近仓库 + 附近地面堆）
4. Place(...)  ← 位置确定之后才扣料
5. Consume(...) 按"随身 → 仓库 → 地面堆"的顺序扣
```

为什么必须这样：如果先扣料再发现位置不可用，玩家会看到"资源没了但房子也没起来"，
而这种状态**无法从任何 UI 上解释**。事务性是让经济操作可信的最低要求。

## 5. 三层物资存储（M3 完成）

| 层 | 载体 | 谁用 | 空间性 | 对应社会关系 |
|---|---|---|---|---|
| 随身 | `AgentStore._inv*` | 一个人 | 跟着人走 | 私人物品 |
| 地面堆 | `GroundStockStore` | 附近的人 | 在地上可见 | 临时共用 |
| **仓库** | `StorageStore` | **整个聚落** | 固定位置、容量大 | **公共财产** |

M8 的贸易（聚落与聚落之间）会成为第四层。
**如果只有一层，"贸易"与"共享"就没有可区分的载体** —— 这是分层的真正理由，
而不是为了"看起来更完整"。

### 5.1 `StorageStore` 的实现选择

按**建筑槽位对齐的平行数组**，而不是 `Dictionary<int, ResourceStock>`：

- 字典的迭代顺序不保证，而这里的状态要进存档与摘要（第 13 节的确定性约束）；
- 槽位数就是建筑容量（几百），稀疏度不高，数组完全够用。

容量为 0 的槽位表示"这里没有仓库"，`Deposit` 直接返回 0（而不是静默写入）。

### 5.2 一个容易漏掉的东西：共享库存必须进摘要

`StorageStore` 不是 `ISimEntitySet`（它是"建筑的附属数据"而不是独立实体），
因此它**不会**被 `HashEntities` 自动覆盖。

实测踩到：把 1000 木材放进仓库，状态摘要**没有变化**，
于是"确定性校验通过"这句话就失去意义了。

**判据**：任何持久状态是否进摘要，标准是"**它会不会影响未来的行为**"，
而不是"它有没有自己的类"。

## 6. 建筑改变世界：M3 的第一个因果链

```text
住房缺口（人口 > 床位）
    ↓  驱动建造效用
采集木材（GatherWood 的"附近有建造需求"项）
    ↓
建造住房
    ↓  床位增加
住房缺口归零 ⇒ 采集木材的公共驱动归零 ⇒ 森林不再被砍
```

这条链有一个非常重要的性质：**它有饱和点**。
"住房缺口"在拿到足够床位之后归零，因此采伐自然停下。

> 与之对比：M2 的"囤积"没有饱和点，结果个体会无限采集。
> **任何"只增不减"的需求最终都会淹没整个行为空间**，
> 所以每个需求都必须回答"什么时候算够了"。

### 6.1 农田是"建筑改变地形"的第一个例子

农田建成时会把 `Tile.Terrain` 改成 `Farmland`。这是本项目里第一次
"人造物永久改变地貌"，也是"人口 → 开垦 → 森林减少"这条链条的起点（第 33 / 97 条）。

## 7. 与其它系统的连接

| 方向 | 连接 | 机制 |
|---|---|---|
| 资源 → 建筑 | 造价 | 木材/石料被扣掉（事务性） |
| 共享库存 → 建筑 | 公共物资 | 扣料优先级：随身 → 仓库 → 地面堆 |
| 人口 → 建筑 | 住房缺口 | `(人口 − 床位) / 人口` 驱动建造效用 |
| 建筑 → 人口 | 床位 | `TotalBeds` 会被 M4 的出生率读取 |
| 建筑 → 地形 | 农田 | 建成时 `SetTerrain(Farmland)` |
| 建筑 → AI | 仓库可见性 | `StoreInBuilding` / 扣料都只在 `StorageSearchRadius` 内找仓库 |
| 建筑 → 表现层 | 渲染 | `Tile.BuildingId > 0` ⇒ 覆盖建筑色调与字形 |
| 建筑 → 摘要 | `HashInto` + `StorageStore.HashInto` | 状态可复现 |

## 8. 测试契约

| 测试 | 覆盖 |
|---|---|
| `BuildingIsPlacedAndAnchored` | 放置成功且 `Tile.BuildingId = slot + 1` |
| `BuildingCannotOverlap` | 同格拒绝第二个建筑 |

| `StorageRespectsCapacity` | 容量上限、不覆盖、无容量槽位拒绝 |
| `BuildingDiagnostics` | 无人干预时房子会不会自己出现 |

## 9. M3 的联调记录

| 现象 | 根因 | 修法 |
|---|---|---|
| **60 天 0 个建筑**，同时人口从 40 掉到 1 | "材料齐备"被写成 **bonus**，于是"住房缺口 1.0 但一点木材都没有"的个体建造效用仍是 1.0 —— 他一直选中建造、跑到工地、失败、再选中建造，**采集永远排不上队** | 改成**门槛**语义（`Threshold(0.98)`）。门槛与加分的区别在这里是生死攸关的 |
| 木材 40 天只采了 241（而 36 人一天能采 288） | 采集只按"自己缺不缺木材"驱动，随身到 30 就停手，永远攒不出建房成本 | 新增"附近有建造需求"（`BuildDemand01`）作为**公共生产驱动**，权重高于"随身已够多"的压制 |
| 房子能建在山顶上 | 山地在规则表里是"可建造"的（矿场需要），被住房共用了 | 允许地形改为**显式列举**（`AllowedTerrains`） |
| 仓库永远不建（60 天 0 个） | 仓库缺口只看"地面堆数量"，而地面堆只有在随身超过门槛时才出现 ⇒ 死锁 | 改为看"聚落攒下的可用木材总量"（随身 + 地面堆 + 仓库） |
| 采石量恒为 0 | 石料需求也挂在"地面堆"上 ⇒ 同一个死锁（**需求 A 依赖 A 的结果**） | 改为"木材已备足 且 石料仍缺" ⇒ `woodReady × stoneMissing` |
| 让门槛贴近实际携带量后人口从 40 掉到 22 | 存放/取回开始互相喂养（M2 的老问题换了参数又出现一次） | 门槛回到 28，取回门槛 6，两者保持明显间距 |
| 摘要不包含共享库存 | `StorageStore` 不是实体集合，不会被自动覆盖 | 在 `StateHash.Compute` 里显式混入 |

**这一组记录里出现了三次同一类错误**：
"判据需要它自己的结果才能成立"（地面堆 → 仓库、石料需求 → 地面堆、囤积 → 存放）。
这类死锁的排查方式很简单：**问一句"这个判据本身需要什么才能成立？"**
