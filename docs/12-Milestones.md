# 12 — Milestones

本文件是**唯一的开发进度真相**。每个里程碑必须满足两个条件才算完成：

1. **可运行**：能启动、能观察、能操作（第 89 条：不允许"开发三个月后才出现第一个可玩版本"）；
2. **有验收**：验收项可机测或可肉眼复核，且写在本文件里。

## 0. 构建通道（所有里程碑共用）

本仓库刻意支持两条构建通道，让"能不能跑"不取决于开发机装了什么：

| 通道 | 前置条件 | 命令 | 说明 |
|---|---|---|---|
| **A（首选）** | .NET 8 SDK | `.\tools\build.ps1 -Mode build` | 自动探测 SDK（参数 → 环境变量 → 默认目录 → PATH） |
| **B（降级）** | .NET 8 运行时 + Roslyn `csc` | `.\tools\build.ps1 -Channel csc` | 直接用 `csc` 编译 BCL-only 源码；引用 assembly 从 targeting pack 取，取不到则从 `shared/Microsoft.NETCore.App/8.x` 过滤出托管 DLL |

**为什么不用 NuGet**：一旦引入任何包（哪怕是 xUnit），通道 B 立刻失效，
"没有 SDK 也能构建"这个承诺就没了。因此：

- 测试用自带的反射运行器（`Tests/Framework` + `Tests/TestRunner.cs`）；
- JSON 用手写的解析器/绑定器（`Foundation/JsonParser.cs`、`JsonBinder.cs`）；
- PNG/zlib 用手写的编码器（`Console/Png`）。

**何时允许引入 NuGet**：仅当出现"自己写明显不划算"的需求（例如需要成熟数学库或
高性能并行框架），且必须同时保留通道 B（用条件编译或替换实现）。

### M0 明确*没有*做的事（留给后续）

- 没有任何 Agent（人口恒为 0）；
- 没有资源采集者（资源只会再生与枯竭，没人消耗）；
- 没有火灾、没有建造、没有聚落、没有存档。

这些不是遗漏，而是**刻意的顺序**：先把"世界的物理规则 + 可复现 + 可观察"做对，
再往上加"活着的东西"。反过来的话，一旦人口与行为进来，任何地基性改动都会
让已经跑出来的世界历史全部失效，调试成本会指数上升。

## M1 — Agent、寻路与 Utility AI（✅ 已完成）

### 目标

让地图上出现**会自己决定做什么**的个体，并让玩家能看清"他为什么这么决定"。

M1 的范围刻意比原计划更大一点：它不只做了"会走路的小人"，而是让个体**能自己活下来**
（采集 → 进食 → 饮水 → 睡眠）。理由是 M1 的验收标准必须是"值得观察的行为"，
而一群走来走去但不会饿、不会累的小人并不构成行为 —— 那只是动画。

### M1 的联调记录（都被测试或文档固化下来）

| 现象 | 根因 | 修法 |
|---|---|---|
| **40 人两天内全部饿死**，且采集统计里食物为 0 | 木材/石料的"可得性"权重（1.2/1.0）压过了食物采集的饥饿项 | 提高 `GatherFoodHungerWeight` 到 2.5；并明确"生存类动作必须在效用尺度上说过非生存类动作"是**正确性**而非平衡问题 |
| 采集/进食统计在涨，人还是在死 | 饥饿只能在 600 tick 一次的决策窗口里被处理 ⇒ 一天最多吃两顿，物理上不可行 | 新增"生存需求打断决策冷却"（`HasCriticalNeed`，阈值 0.7） |
| "有点饿时不想采食物"导致补偿下界把生存动作压住 | 效用合成器带补偿因子 ⇒ 被门挡住的动效停留在下界上 | 新增 `Survival` 曲线，让生存动作在低输入区就拿到高分 |
| 采集量 vs 消耗量严重失衡（每人每天需 ~11 食物，实际只采 ~9） | 参数不匹配（食物容量 24/格、每次采集 5） | 容量提到 60/格、每次采集 24；并在文档里写出这份"口粮账" |
| 个体站在石头上"想砍树"却不采食物 | `GatherWood/GatherStone` 的"需求"用了 `1 − 储量/参考量`，符号语义反了 | 改为"储量充足度"作为负权重项，并写清符号约定 |
| 测试断言自己制造失败 | ① 断言"对角移动两侧都必须可走"比实际规则更严；② 用 `DeathsThisTick` 事后检查（已被清空）；③ 未固定起终点（随机地图上可能是水） | 三条都改对判据，并把教训写进测试注释 |

### M1 明确没有做的

- 没有出生（人口只减不增 ⇒ 长跑必然灭绝，这是 M4 的动机）；
- 没有聚落、没有共享库存、没有建造；
- 没有关系与家庭；
- 没有记忆与已知地点（每次都靠"视野内搜索"，探索的结果不被保留）。

## M2 — 生存经济：物资堆、野生动物与迁徙（✅ 已完成）

### 目标

把 M1 的"个体能活"升级为"群体能经营"：
出现**共享物资**、**生态链**与**第一次被迫迁徙**。

M2 的重点不是加动作，而是让"资源 → 消费 → 缺口 → 行为改变"这条链可观测。
具体来说：物资开始在地上堆积（M3 仓库的前身）、砍树开始有生态代价（猎物变少）、

### M2 的联调记录（每一条都固化成了注释、文档或测试）

| 现象 | 根因 | 修法 |
|---|---|---|
| **"存放/取回"从来没被选中**（统计全 0） | 门槛 25 高于实际携带量；而且"附近有堆"被当作**门槛**，没堆时把整个动作打到 0.15 倍 | 门槛改为按"过度囤积"判断；引入 `Consideration.IsBonus` 区分门槛与加分 |
| **改成 14 之后变成空转**：229,855 次决策有 201,484 次在"存放" | 存放门槛低于取回门槛 ⇒ 两个动作互相喂养（放下→变少→取回→变多→再放下） | 存放门槛 60、取回门槛 8，两者必须有明确间距 |
| **87% 的决策都在"迁移"** | 用"离家距离"（结果）当迁移意愿（原因），形成自反馈：越走越远 ⇒ 越想迁移 | 新增显式的**迁移意愿**字段（`IsMigrating`），由迁移系统授予、动作层只负责执行 |

### 踩坑记录（每一条都固化成了注释或测试）

1. **`ChunkGrid` 聚合统计是"派生数据"，但必须进存档。**
   直觉上它由地形聚合而来、重算一遍就好，但它是**增量维护**的，
   而 AI 真的会读它（`ActionSearch.TryFindWaterAccess` 先看 `WaterTiles == 0`
   决定要不要跳过这个 chunk）。不存的表现：读档瞬间摘要完全一致
   （chunk 统计不进摘要），到第 31 tick 才分叉，且 8 条随机流逐位相同。
2. **"存活列表的顺序"也是状态。** `WildlifeSystem` 按存活列表遍历并消耗随机数，
   而摘要按**槽位升序**计算 —— 所以顺序问题在摘要里根本看不见。
   恢复成升序会导致第 1 tick 就把随机数分给不同的动物。
3. **小数进度（`MoveProgress`）必须进存档。** 它不进摘要，但决定"下一 tick
   会不会跨到下一格"。不存 → 移动节奏错开一格 → 第 2 tick 分叉。
4. **"自己存、自己读"的测试会掩盖 seed 相关的 bug。**
   读档时忘了恢复 `World.Seed`，而所有测试都恰好传了同一个 seed，
   于是这个 bug 在整套测试里完全隐藏，直到用 CLI 做端到端验证才暴露。
   *教训：验证"恢复了什么"的测试必须让**输入**与**期望值**不同。*
5. **手写诊断代码本身也会错。** 第一次定位分叉时，把"直接跑的那份"
   提前跑到了终点，两边根本不在同一个 tick 上，于是打出一堆毫无意义的差异。
6. **"存进去的必须正好是摘要会读的那些值"。** 迁移次数有两个计数器
   （`Stats.TotalMigrations` 与 `Migration.TotalMigrations`），
   存了后者而摘要读前者，于是 `stats` 段永远对不上 ——
   而小规模测试里两个值恰好相等，把问题一路藏到端到端验证。
7. **干预仍然会推进 `RngStream.Agents`**（为新个体抽性格与名字）。
   这是**允许且不可避免**的，测试与注释都写清了边界，
   而不是把它伪装成"完全隔离"。

## M4 — 农业、出生与人口（✅ 已完成）

### 目标

补上这个世界**唯一缺失的机制**：出生。

M2/M3 的长跑结论非常明确：**没有出生 ⇒ 人口单调下降 ⇒ 100 天后归零**
（实测 150 天：38 例衰老、2 例脱水、0 例饥饿）。
M4 要让世界第一次出现"人口自己增长"的阶段，并且让增长**被住房与食物约束住**。

### 交付内容（全部落地）

- **出生系统**（`Core/Systems/BirthSystem.cs`）：
  `P = Base × FoodFactor × HousingFactor × HealthFactor × (1 − 人口压力)`；
- **家庭雏形**：`TickPairing` 用"同住/同地"近似伴侣（M6 换成真实关系），
  按槽位升序配对 ⇒ 与遍历顺序无关；新生儿占空床、性格从双亲遗传（对称突变）；
- **儿童阶段**：`LifeStage.Child`，不参与重体力劳动（`Farm` 动作效用里是**门**）；
- **农业产出**：`Yield = Base × 地力 × 湿度 × 天气 × 劳动力`，每日结算进共享库存；
- **`Farm` 动作**（耕种）：把劳动量记到农田上 —— 于是"有田"与"有人种"是两件事；
- **建筑衰减**：无人维护每日掉耐久，归零即倒塌（给"建造"补上负反馈）；
- `docs/08` 出生部分已补（见该文档的出生小节）、`docs/09` 补 3 个故事、`docs/15` 补参数。

### M4 的联调记录（每一条都是"机制存在但不可达"的静默失效）

这四条的共同特征：**不报错、不崩溃，症状只是一个安静的 0**。

| # | 症状 | 根因 |

| 4 | 配对数 5 天内从 16 对崩到 3 对 | 健康被误做成**配对资格**而不是乘性因子 ⇒ 某人一虚弱伴侣关系就被清理规则拆掉 |
| 5 | 人口 40 → 0，死因以脱水为主 | 跨界参数失配：M3 的 `Ai.InventoryComfort = 45` **越过了** M2 的 `GroundStocks.SurplusThreshold = 28` ⇒ `surplus` 恒为满值，"存放"占 **75%** 的决策，把进食/饮水/睡眠全挤掉 |

第 5 条尤其值得记：判据（"存放门槛必须高于平时携带量"）从来没写错，
错在两个互相耦合的参数**分处两个配置段**，其中一个被后续里程碑改动时另一个静默失效。
现在它由 `M4Tests.DepositThresholdMustExceedInventoryComfort` 逐次构建时断言。

另外把**初始人口的年龄散布**了（原先全是 `ageDays: 0` = 同一天出生，
会在 90–100 天之间整批同时老死，200 天必然归零）。
那不是"平衡没调好"，是初始条件本身不成立。

## M5 — 玩家工具、灾害与存档（核心已实现，长期平衡待打磨）

### 目标

让玩家第一次能**毁掉条件**，而不只是"加东西"。

在此之前，玩家能做的干预都是加法（加人、加资源、加地力），
而加法实验很容易退化成"看它涨"，因果链很短。
任务书第 68 / 94 条要求的最小因果证明是：

```text
玩家烧掉一片森林 → 人口增速下降
```

这条链之所以是 M5 的核心，不是因为"火很酷"，而是因为它**同时穿过三个系统**：

```text
火 → 森林减少 → 木材减少 → 盖房变慢 → 床位不足 → 出生下降
              ↘ 猎物栖息地减少 → 打猎收益下降 → 食物下降 ↗
```

后果沿着系统之间的耦合自己扩散出去，玩家只按下了一个"点火"。

  暴雨 / 干旱 / 瘟疫 —— **没有"杀死一片人"这种直接产出结果的按钮**；
- **规则开关**（`SimConfig.Rules`）：`NoDeath` / `HighBirthRate` / `FastAging` /

### M5 联调记录：三个"机制存在但被静默否掉"的失效

它们的共同点依旧是**不报错、不崩溃，症状只是一个安静的 0**：

| # | 症状 | 根因 |
|---|---|---|
| 1 | 200 天 0 起火，且实验方向反了（床位 24 vs 20） | 火灾借用 `Events` 流，而**天气也在用同一条流** ⇒ 点火改变了天气序列 ⇒ 因果无法归因。新增独立 `RngStream.Fire` |
| 2 | 200 天 0 起火（第二层原因） | 全图湿度**长期钉在 1.0**：`clamp01(m + delta)` 是加法+截断，而"变湿"比"变干"强一个数量级，且 Cloudy 几乎不干（−0.001）⇒ 干燥度≈0 |
| 3 | 概率算对、路径也对，仍然 0 起火 | 自然点燃**只挑一格就放弃**，9 次全部随机落到水面/山地/裸地 ⇒ 败在采样方式上。改为"硬门只留燃料 + 湿度温度降级为概率因子 + 有界重试" |

第 2 条同时让另外两件事失效，值得一提：
**农田产量的湿度因子**被钉死在 1.0（等于没有这一项），
**干旱**永远无法真正把地表弄干（只在 `CropFactor` 上体现）。
一个死状态往往同时掩盖多个机制 —— 这也是为什么"某个因子看起来没作用"
值得追到底，而不是绕过去。

### 方法论增量

第 3 条促成了一个新的通用做法：**给"安静的 0"配两个计数器。**
`FireSystem` 现在暴露 `NaturalIgnitionRolls / Hits / Rejected`：

* 判定为 0 ⇒ 调用路径断了；
* 判定很多而通过很少 ⇒ 概率或筛选有问题；
* 通过很多而点燃为 0 ⇒ 逐格条件把候选全否了。

只看最终结果数字，这三者是**无法区分**的。

### 批量验收暴露的架构缺陷 —— **已修复**

（下面保留问题被发现时的原始记录，因为"手工场景全过、批量验收立刻打脸"这个过程本身就是教训。）

#### 原始记录

新增 M7BatchAcceptance（SBOX_SIM_BATCH=1）做 20 种子 x 100x100 x 40 人 x 200 天的验收。
**前四个种子的结果就已经说明问题**：

```text
seed 70001 人口 58 聚落 1 (活跃 0) 首成 34天 最高等级 Camp
seed 70138 人口 40 聚落 0 (活跃 0) 首成 —   最高等级 Camp
seed 70275 人口 22 聚落 1 (活跃 0) 首成 10天 最高等级 Camp
seed 70412 人口 10 聚落 2 (活跃 0) 首成 12天 最高等级 Camp
```

**两个症状，同一个根因：**

1. **聚落全部解散（活跃 0），哪怕当时有 58 人活着。**
2. **最高等级永远停在 Camp。**

根因是形成逻辑用了**全体存活个体的质心**，再在质心附近半径内数人。
人分散在一整张地图上时，全体质心会落在**没人的地方**，于是"质心附近有几个人"很小，
聚落被自己的解散阈值判死；等级也永远上不去。手工 44x44 场景之所以通过，
只是因为那里人本来就挤在一起 —— **测试场景太友好，掩盖了架构问题**。

更根本的是第 3 个后果：**全体质心在原理上只能产出一个聚落**，
所以" >=5/20 个种子有 >=2 个聚落"这条验收判据在当前架构下**永远不可能达成** ——
那不是参数问题，是架构问题。

#### 修复：用空间聚类替换全体质心

按上面的方案实施：按 `ClusterRadius` 分格、用**并查集**合并相邻占用格
（合并顺序由格遍历顺序决定 ⇒ 确定性由构造保证），每个连通块算一个"人群"，逐个评估。

| 70138 | 聚落 0，Camp | 聚落 0，Camp |
| 70275 | 聚落 1（活跃 0），Camp | 聚落 3（**活跃 1**），**Village** |
| 70412 | 聚落 2（活跃 0），Camp | 聚落 2（活跃 0），Camp |

1. ~~**5/20 个种子完全没有形成聚落**~~ —— **已查清**：瓶颈是**仓库恒为 0**。
   `M7ClusterDiagnostics` 显示那 4 个种子的"最大人群住房/仓库"分别是 **18/0、20/0、3/0** ——

   而 M4 为治"存放挤掉生存动作"把 `SurplusThreshold` 从 28 提到 70 ⇒ 地面堆变得罕见。
   已给缺口加了一条"人口"来源。**继续测下去发现原因是两个，不是一个**：
   补测"被选中次数 / 仓库施工中与完工数 / 随身木材"之后得到

   ```text
   seed 70138 -> 选中 1297 次；施工中 0 完工 0；随身木材 0
   seed 71508 -> 选中    0 次；施工中 0 完工 0；随身木材 294
   seed 71645 -> 选中    0 次；施工中 0 完工 0；随身木材 42
   ```

   * **70138（选中却从不完工）**：`Evaluate` 里确实有材料门，但
     **`Evaluate` 算的 `material` 与 `TryStartBuilding` 实际需要的材料不是同一个口径** ——
     于是一个永远无法开工的动作持续赢得竞争（1297 次），每次都在开工时失败，
     每次都花掉一个本该用于"去砍木头"的决策。**这不是机制不可达，是机制在空转。**
   * **71508 / 71645（从未被选中）**：木材有 294 / 42、`populationGap` 也 ≥0.5，
     说明它是在与 `BuildHouse` 等动作竞争时输掉的。

   **下一步试过了，并且失败得很有价值**：把 `Evaluate` 改成在**工地坐标**上算材料
   （并抽出 `PooledAmountAt` 让两边共用），实测**没有修好**（70138 仍然 0 次开工），
   而且行为整体偏移（该种子的住房从 18 变成 0）。
   核对执行侧发现 `AvailableFromPiles` 用的半径与 `PooledAmountAt` **完全相同** ⇒ 不是半径问题。

   **正确结论：这道门无法靠"统一坐标"修好，因为问题的本质是物流。**
   动作管线是**决策 → 移动 → 执行**：`Evaluate` 时刻算一次工地，个体走过去，
   而执行时 `SelectTarget` **会重新选一次工地** —— 两个工地本来就不是同一个。
   只要个体身上没有材料、而材料在别处，这个动作就注定空转。
   真正的修法是**物资搬运**（开工前把料搬到工地，或让"建造"派生出"去取料"子目标），
   属于 **M8 的物流链**。

   该改动已**回退**（一个被实测证伪的改动留在代码里比不留更糟），
   推理过程保留在 `BuildActions.cs` 的注释里，当前口径标记为**已知设计缺口**。
2. **1/20 个种子人口归零（灭绝）** —— 与 M4/M5 观察到的种子敏感性一致，属已知的世界稳定性问题。

## M8 — 贸易、外交与冲突（部分实现：价格与个体冲突压力）

当前有全图价格计算和个体冲突压力；实际聚落交易、贸易路线、外交和文明实体尚未交付。

### 已完成：`TradeSystem`（价格）

`Price = Base × ((Demand + ε) / (Supply + ε)) ^ α`（任务书第 71 条）。
ε 是平滑项（没有它，供给为 0 会让价格趋于无穷、需求为 0 会让价格变成 0）；
上下限（0.2×~8× 基准价）**是语义的一部分**而不是防溢出的补丁 ——
价格若可以是无限大，任何依赖它的决策都会在极端情况下崩掉。

**关键设计：整个系统不存任何状态。** 价格是现有状态的纯函数，
所以不进存档、不进摘要，读档后重算即可。
判据：**能在一秒内重算出来的东西就不要存。**

**`M8Tests` 6 项通过**（其中 `PriceNeedsNoSaveAndRecomputesIdentically` 锁定"不存档也能一致"）。

#### 测试抓到两个真实 bug（同源：`ResourceKind` 从 1 开始）

1. **下标字面量**：累加用 `(int)ResourceKind.Wood`(=2)，取价却写 `supply[1]` ⇒
   木材的价格是用**食物**的供给算的。症状是**方向反了**：
   供给 76 → 5996（79 倍），价格却 0.681 → 0.915。
   **只测"价格是正数且在界内"永远抓不到它** —— 抓住它的是方向性断言。
2. **数组长度按"种类个数"开**：`supply[4]` 而 `Iron` = 4 ⇒ 越界。

教训：**枚举类型的下标一律强转，绝不写字面量；数组长度按最大下标开。**

### 已完成：`ConflictSystem`（冲突压力，第 74 条）

`WarPressure = 资源冲突 + 领土冲突 + 侵略性 + 历史敌意 − 贸易收益 − 关系`。
四项推、两项拉 —— **战争不是被触发的，是被推到超过拉之后自己发生的。**
同样是纯派生量（不存档、不进摘要），已接到 `AttackAction` 的效用上；
它**不替代**敌意门（门答"能不能打"，压力答"有多想打"）。

**测试抓到的设计缺陷**：第一版四项"推"权重和 = 3.5，于是只要资源冲突拉满压力就贴着上限 ——
挚友 / 陌生人 / 仇敌算出来**都是 1**，"关系是拉项"在数值上完全看不出来。
归一到和 = 1.0 之后，`1.0` 有了明确含义："所有推力拉满且无任何拉力"。
`M8ConflictTests` 7 项全过，且**全部是方向性断言**（能抓住"整体反向"这类 bug）。

## 优先级原则（防止 Feature Creep）

任何新功能进入计划前必须回答三个问题（第 90 条）：

1. 它**增加涌现性**吗？（会让系统之间产生新的相互作用链吗）
2. 它**增加玩家能动性**吗？（多一个"条件旋钮"而不是"结果按钮"吗）
3. 它**增加可观察性**吗？（玩家能更容易理解发生了什么吗）

三个都答不上来 → 不做。见 [11-MVP-Scope](11-MVP-Scope.md) 的禁项清单。

**第一阶段的禁项**（第 72 条）：完整科技树、几十种资源、几十种职业、复杂装备系统、
复杂战斗系统、外交系统、政治系统、宗教系统、完整金融经济、超大地图、多人联机、
3D 高质量美术、复杂任务系统、完整剧情系统。

理由不是"做不了"，而是：**真正需要先验证的是"10~30 个 NPC 在地图上自己生活是否有趣"。
如果这个核心没有乐趣，更多内容不会让游戏变好。**
