# 02 — System Architecture

本文件规定**谁能读谁、谁能改谁**。这是防止模拟项目长成一团泥巴的第一道防线，
也是"新增系统"时最该先看的一页。

---

## 1. 依赖方向（编译期强制）

```text
                     ┌───────────────────────────────┐
                     │   SandBoxSim.Console（表现层）  │
                     │   TUI / PNG / CLI / 报告 / 工具  │
                     └───────────────┬───────────────┘
                          只读查询 + 干预接口（单向）
                                     ↓
   ┌─────────────────────────────────────────────────────────────────┐
   │                    SandBoxSim.Core（纯模拟内核）                   │
   │                                                                 │
   │   Foundation ────────────────────────────────────────────────┐  │
   │   （RNG/噪声/哈希/数学/曲线/JSON/配置）                        │  │
   │        ↓                                                      │  │
   │   World（Tile/地形规则/世界生成/空间索引/天气/日历）             │  │
   │        ↓                                                      │  │
   │   ResourceSystem（再生·采集·枯竭）    Pathing（M1）            │  │
   │        ↓                                    ↓                 │  │
   │   Agents（数据/需求/库存/性格 M1）  ←  Buildings（M3）          │  │
   │        ↓                                    ↓                 │  │
   │   Ai（考虑项→效用→决策 M1） ──→ Actions（执行管线 M1）          │  │
   │        ↓                                                      │  │
   │   Settlements（共享库存/领土 M4/M7）                            │  │
   │        ↓                                                      │  │
   │   History（EventLog/统计/时间线）                              │  │
   │        ↓                                                      │  │
   │   Civilization（贸易/外交/冲突 M8）                             │  │
   │        ↓                                                      │  │
   │   Simulation（Tick 管线 + 干预接口 + 不变量校验）  ←────────────┘  │
   └─────────────────────────────────────────────────────────────────┘
```

**铁律**：

1. **下层不可见上层**。`Foundation` 不知道 `World` 存在；`World` 不知道 `Agents` 存在。
   违反这条的后果是循环依赖，最终导致"改资源公式要重编译 AI"。
2. **`Core` 不认识 `Console`**。表现层需求必须通过 `Simulation` 暴露的只读查询接口获得。
   一旦 Core 里出现 `Console.WriteLine`，模拟就不再可重放。
3. **同层之间只能单向**。例如 `ResourceSystem` 可以被 `Ai` 查询，但 `ResourceSystem`
   不能反过来调用 AI（那会让"环境过程"依赖"决策过程"，不变量会被 AI 的改动污染）。

> 目录名与命名空间有意不完全一致：`src/SandBoxSim.Core/World/` 里的命名空间是
> `SandBoxSim.Core.Environment`，因为 `World` 已经是一个类名（避免 `World.World` 这种读起来
> 像 bug 的写法）。目录名保持 `World` 是为了新人按直觉能找到文件。

## 2. "谁读谁 / 谁改谁"矩阵（M0 实装部分）

图例：**R** = 只读，**W** = 写入，空白 = 不接触。

| 系统 ↓ \ 数据 → | Tile 地形 | Tile 资源量 | Tile 湿度/温度 | 天气 | 日历 | 空间索引 | 事件日志 | 统计 |
|---|---|---|---|---|---|---|---|---|
| `WorldGenerator` | W | W | W | | | W | | |
| `WeatherTick`（Simulation） | | | W | W | | W | W | |
| `ResourceSystem` | | W | | R | | W | | W |
| `Simulation.Tick`（管线） | | | | R | W | W | | W |
| `EventLog` | | | | | | | W | |
| `SimulationStats` | | R | R | R | R | R | R | W |
| `StateHash`（摘要） | R | R | R | R | R | | | R |
| **Console** 全部 | R | R | R | R | R | R | R | R |
| **干预接口** | W | W | | W | | W | W | |

**读这张表的方法**：

- 找某一列，看有谁会写它 → 写者必须唯一或必须有序，否则会出现"谁最后写谁说了算"的竞态。
- 找某一行，看它读了什么 → 这是这个系统的输入契约，改动输入必须同步改文档。
- **任何系统都不允许"既读统计又改统计"**（统计是模拟的镜像，不是模拟的一部分）。

### 2.1 M0 实装系统的接口契约

| 系统 | 文件 | 读 | 写 | 不做什么 |
|---|---|---|---|---|
| 世界生成 | `World/WorldGenerator.cs` | `SimConfig`（WorldGen/Resources/World）、seed | 返回 `Tile[]`（纯函数，不改任何全局状态） | 不碰 RNG 流（自己派生独立噪声场）、不写事件日志 |
| 空间索引 | `World/ChunkGrid.cs` | `Tile[]` | 自己的 Chunk 聚合缓存 | 不做世界状态的真相（真相永远在 Tile 数组里） |
| 资源系统 | `ResourceSystem.cs` | `SimConfig.Resources`、Tile 资源节点 | Tile 资源量、植被、自家统计 | 不决定"谁去采集"（那是 AI 的事）|
| 天气 | `World/Weather.cs` + `Simulation.WeatherTick` | 平均湿度/温度、RNG(Weather 流) | `Weather` 自身、Tile 湿度/温度 | 不直接改变地貌（火灾另有系统） |
| 事件日志 | `History/EventLog.cs` | 各系统传入的事件 | 环形缓冲 | 不反向影响任何系统（只被读） |
| 统计 | `SimulationStats` | 全图查询结果 | 自家曲线数组 | 不修改模拟状态（否则"打开面板"会改变世界） |
| 摘要 | `StateHash` | 全部状态 | 无（返回一个 ulong） | 不消耗随机数、不改任何状态 |

> **踩坑记录**：`ResourceSystem.Regenerate` 早期版本在"没有任何资源变化"时也调用
> `MarkDirtyAt`，导致每 tick 全图重算 chunk 统计（10 万格 × 每 tick）。
> 现在只有在 `after != before` 时才标脏 —— 这是"写者必须精确"的一个具体例子。

## 3. 反馈环清单

第 66 条要求：每加入一个机制，必须分析它的正反馈与负反馈。
本表是**唯一**的反馈环登记处，新增机制必须在这里留行。

### 3.1 已实装（M0）

| 环 | 类型 | 链路 | 阻尼来源 |
|---|---|---|---|
| 天气-湿度自强化 | 正 | 雨 → 湿度↑ → `ChooseNext` 更倾向继续下雨 | 天气有持续小时上限（4~16h 强制重抽） |
| 干旱-火险自强化 | 正 | 干旱 → 湿度↓ → 火灾风险↑ → 森林↓ → 湿度↓（少蒸腾） | 干旱同样有持续时间上限；雨会打断 |
| 资源再生-存量 | 负 | 采伐 → 存量↓ → Logistic 再生量↓ | 这本身就是阻尼：过度采集造成不可逆损伤 |
| 湿度-蒸发 | 负 | 雨 → 湿度↑；晴天/干旱 → 湿度↓ | 湿度被 clamp 在 [0,1]，饱和后不再上升 |

### 3.2 已规划（M1–M8，落地时移到上表并补实测数据）

| 环 | 类型 | 链路 | 阻尼来源 |
|---|---|---|---|
| 人口-劳动力-产出 | 正 | 人口↑ → 劳动力↑ → 产出↑ → 粮食↑ → 人口↑ | — |
| 人口-消耗-稀缺 | 负 | 人口↑ → 消耗↑ → 稀缺↑ → 死亡/迁出 → 人口↓ | 这是主要阻尼 |
| 建造-住房-出生 | 正 | 木材↑ → 住房↑ → 出生率↑ → 劳动力↑ → 木材↑ | 木材再生速度 |
| 农业-地力-产量 | 负 | 连续耕作 → 肥沃度↓ → 产量↓ | 休耕 / 天然恢复速率 |
| 贸易-价格 | 负 | 缺口 → 价格↑ → 更多人做该职业 → 供给↑ → 价格↓ | 这是最重要的负反馈之一（第 49 条） |
| 战争压力 | 正/负 | 资源冲突 → WarPressure↑ → 战争 → 双方资源↓ → 压力↓ | 停战与关系修复 |
| 迁移-机会摊薄 | 负 | 新地资源好 → 迁入 → 本地资源被分摊 → 优势消失 | 资源再生上限 K |

## 4. 表现层的边界（Console 的合法行为）

`SandBoxSim.Console` 可以做：

- 读 `Simulation` / `World` / `EventLog` / `SimulationStats` 的公开只读成员；
- 调用 `Simulation.Intervene*` 系列方法（这是**唯一**的写入口）；
- 用**自己的**随机源（例如"用新种子重生成世界"）—— 但它只影响"选哪个世界"，
  一旦选定，模拟内部依然完全确定性；
- 持有渲染缓存（Cell 缓冲、颜色表、相机、路径可视化）。

**禁止**：

- 直接修改 `Tile`、Agent 数据、库存；
- 读 `Simulation.Random`（那会改变随机序列，破坏可复现性）；
- 在渲染里调用 `sim.Tick()`（时间推进只由 GameLoop 的累加器决定）。

> 特例说明：玩家工具在 Console 里"看起来"改变了世界，但它调用的是
> `Simulation.InterveneSetTerrain` 这类中间层方法，由中间层负责同步规则、空间索引与事件日志。

## 5. 数据流的三种时序

| 时序 | 触发 | 例子 |
|---|---|---|
| **每 tick** | `Simulation.Tick` | 时钟推进、空间索引刷新、动作执行、移动 |
| **每小时** | `TickHour` | 天气、资源再生、统计采样（M4+ 还有分工需求刷新） |
| **每天** | `TickDay` | 年龄、出生、死亡、迁移、聚落评估、日样本（M2+） |
| **事件驱动** | 玩家干预 / 灾害 / 状态阈值 | 地形改造、火灾点燃、聚落升档 |

顺序是**确定性契约**，不可配置：任何两个系统之间的顺序改动都会改变世界演化结果，
因此顺序写死在 `Simulation.Tick` 里并配有测试（`WorldTests.HourEventsFireOnce` 等）。

## 6. 新增系统的接入检查清单

1. 它属于哪一层？（能不能放在更下层？）
2. 它读什么、写什么？填进 §2 矩阵。
3. 它有正/负反馈吗？填进 §3。
4. 它需要新的随机数吗？用哪条 `RngStream`？（不允许随便开新流：改流会破坏旧存档）
5. 它需要新配置项吗？加进 `SimConfig` 与 `config/sim.default.json`，
   并在 `docs/15-ConfigReference.md` 写明含义与影响链。
6. 它的状态怎么进摘要？（实现 `ISimEntitySet.HashInto`，或加进 `StateHash`）
7. 它有 Debug 手段吗？（检查器字段 / 热力图 / 日志）
8. 它可能造出什么故事？写进 `docs/09-EmergentStories.md`。
9. 它有测试吗？（至少：确定性、边界、不变量）
10. 它会不会破坏某条已有测试？（跑 `.\tools\test.ps1`）
